## 3. Migration assessment

**Is 0037 next?** Yes. Journal `idx: 37`, `when: 1785039545644` > 0036's `1784464092263`, no gap or
collision; `meta/0037_snapshot.json` `prevId` chains correctly to `meta/0036_snapshot.json`.

**Additive?** Yes. Destructive-statement scan returns **zero** — no `DROP TABLE/COLUMN/INDEX/CONSTRAINT`,
no `TRUNCATE`, no `DELETE`, no `ALTER COLUMN … TYPE`, no `RENAME`. The single `DROP TRIGGER IF EXISTS`
sits inside the guard block and is immediately followed by `CREATE TRIGGER` — an idempotent recreate.

**Drizzle parity?** Excellent. Column-for-column, index-for-index, CHECK-for-CHECK across all 8 tables,
33 CHECKs and 31 indexes, `schema.ts` and the SQL agree.

**Tables created (8):** `wizmatch_company_policies`, `wizmatch_company_policy_events`,
`wizmatch_company_duplicates`, `wizmatch_reply_mailboxes`, `wizmatch_outreach_batches`,
`wizmatch_outreach_enrolments`, `wizmatch_outreach_events`, `wizmatch_suppression_events`.

**Existing tables touched:** `wizmatch_companies` (§10.8 ADD COLUMN + FK), `wizmatch_suppression_list`
(§10.8 two ADD COLUMNs + FK), and the six §10.10.1 additive indexes on `users`, `contacts`,
`contact_channels`, `wizmatch_companies`, `wizmatch_job_signals`, `wizmatch_requirements`. Nothing else.
No Growth, SEO or D2C table is altered.

**The blocker (C-1, fixed).** Every composite FK references a parent on `("tenant_id","id")`, and
drizzle-kit emits every `CREATE INDEX` **after** every `ADD CONSTRAINT`. PostgreSQL resolves the
referenced unique index at `ADD CONSTRAINT` time, not at `COMMIT`
(`tablecmds.c` `transformFkeyCheckAttrs`), so the first such statement raises SQLSTATE **42830**
*"there is no unique constraint matching given keys for referenced table"* and aborts the transaction.

- All **29** composite FKs were affected. Measured: 29 ordering violations before the fix, 0 after.
- The two FKs inside `DO $$ … EXCEPTION WHEN duplicate_object` blocks were **not** protected — that
  handler catches 42710, not 42830.
- No prior migration creates any `(tenant_id, id)` unique index, so none of the nine targets pre-existed.
  This was checked, not assumed; it is what rules out "it would have worked incrementally in prod".

Fix: the nine `CREATE UNIQUE INDEX` statements are **moved** ahead of the FK block inside a marked
`MANUAL REORDER (0037)` block. No statement text is altered, added or removed — `db:generate` still
reproduces the same set, only in the order Postgres cannot execute.

**Lock exposure (unchanged, G1-gated).** The three `CREATE UNIQUE INDEX` statements on `users`,
`contacts` and `contact_channels` are not `CONCURRENTLY` and take a write-blocking lock on Growth's
shared tables for the build duration. This is U-7, already an owner decision gating G1, and §10.11.4
requires the duration to be measured on a production-sized restore first.

## 4. Tenant-isolation assessment

Clean, and the strongest part of the schema work.

- All 8 new tables carry `tenant_id uuid NOT NULL REFERENCES tenants(id)`.
- **Every** index on the new tables leads with `tenant_id` — zero exceptions.
- **29 composite entity FKs, zero naked single-column FKs to an entity.** The 8 FKs to `tenants(id)`

- Every composite FK's target has a supporting `(tenant_id, id)` unique index — and, after C-1, one

matches the table, not the prose — a PRD counting nit (L-2), not a code defect.

## 5. Resolver assessment

**Phase 0 (inheritance) was correct as submitted.** `resolveDimension()` walks per dimension and takes
the first non-null value, recording `scopeKey` and `policyId` — not per row, which is the classic bug
here. The §8.1 worked example (a `location:bengaluru` row setting only `outreach_eligibility='paused'`
leaves the company-wide `relationship_type` and `external_hiring_policy` in force) holds and is tested.

- L0 missing root → `deny` / `policy_missing_root` / `effectiveLevel 0` / `effective` all null. ✅
- **No legacy fallback.** Zero references to `wizmatch_company_intelligence` or any legacy `.status`
  anywhere in `src/modules/outreach`. D-1/A-22 satisfied. ✅
- §8.1.1 unresolvable scope → `deny` / `scope_unresolvable`, checked on scope **type** existence rather
  than label match, which is the fail-closed reading. `business_unit` correctly denies any request
  without an explicit label. ✅
- L1c (non-overridable block at a narrower scope) scans the raw applicable rows rather than the
  Phase-0-resolved dimension, so a narrower `eligible` row cannot mask a hard block. ✅
- L1 keys on `is_non_overridable`, not `block_class`, per §8.3. ✅
- `campaign_family` is never consulted for permission. ✅
- `buildScopeKey()` is the sole producer of `scope_key`; normalisation is deterministic and total;
  malformed input throws rather than coercing; `region:` is constrained to `india|us` in both TS and a
  DB CHECK. ✅
- Root completeness and the no-op-row rule are enforced by DB CHECKs
  (`..._root_defines_all_chk`, `..._scoped_overrides_one_chk`). ✅

**Phase 1 (decision assembly) is where the defects were** — five of them, all fixed. See §9.

**Immutability.** The trigger protects every policy decision column and permits only `superseded_at`
and `superseded_by_policy_id` to change. Supersession therefore remains possible while a changed
decision must be a new row plus an event, exactly per D-3/A-24. ✅

## 6. Lock and duplicate assessment

**Enrolment states.** The 15 states in the SQL CHECK and in `WIZMATCH_ALL_ENROLMENT_STATES` are
identical, order for order. The 8 live states are exactly D-6's list, and all four partial-index
predicates carry the same 8. **A reply does not release the lock**: `replied`, `awaiting_action`,
`positive_reply`, `referral_received` and `conversation_open` are all in the live set, in both SQL and
TypeScript. The 7 terminal states release it. `manually_released` requires actor and reason, CHECK-
enforced on both the enrolment and the event row. ✅

The §10.6.2 constraints are all present: the company cold-email lock, the contact live-uniqueness, the
A-30 email-normalised predicate, and the A-20 non-cold overlap constraint.

**Duplicates.** The schema is sound — both company ids as composite FKs, `CHECK (company_a_id <
company_b_id)` preventing self-pairing and bidirectional double-recording, and a pair unique index.
But `wizmatch_company_duplicates` was **never read** (H-5): §8.2 L5 and §8.8 were unenforced, so a
company under duplicate review could still be queued, exported and sent. Now enforced, checking **both
sides** of the pair — because pairs are stored ordered, a `company_a_id`-only lookup would miss half of
all suspects. Free preparation still runs.

Remaining (PR 4, correctly out of scope): the duplicate review UI, merge / confirm-separate, and the
policy-divergence warning.

## 8. Test assessment

**Before:** 4 files, 37 tests, all passing. **After:** 6 files, 60 tests, all passing.
Full suite: **99 files, 867 tests green**; `npm run build` exits 0; `git diff --check` clean.

The submitted tests were real where they existed — the scoped-inheritance test asserts per-dimension
`scopeKey` provenance and would fail if the resolver were wrong, and `wizmatchReasonCodes.test.ts`
mechanically derives the six-code prep set from the taxonomy rather than restating it.

Three weaknesses found:

1. **The gate test's db mock discards `.where()` entirely**, returning the full fixture regardless of
   predicate. Every tenant-isolation and suppression-normalisation assertion in that file therefore
   *cannot fail* — including the one named as the A-1 regression. This is why H-3 survived a passing
   suite. The new contract suite uses a predicate-capturing mock.
2. **No test pinned the migration's SQL text to the exported state constants**, which §22.2 #8 and
   §10.6.2 both call for. The migration is necessarily a frozen copy, so only a test can hold them
   together.
3. The 8×8 routing test loops all 64 combinations but asserts only *shape*, so ~59 cells cannot fail on
   a wrong route or mode.

**New tests, each verified to fail on the defect it covers:**

- `wizmatchOutboundMigrationContract.test.ts` (8) — FK/index ordering (control: 29 violations detected
  on the pre-fix file, 0 after), state-list parity, destructive scan, untouched suppression index,
  absence of `admin_override`/`suppression_scope`/`scope_ref_id`.
- `wizmatchOutreachGateContract.test.ts` (15) — the §8.6/§8.7 routing outcomes, L1c derived prep,
  suppression column lowercasing, grain-accurate reason codes, L5 duplicate containment, and a
  tsc-checked `@ts-expect-error` for the brand. **Control run on the brand test:** with the string brand
  restored, `tsc` reports *"Unused '@ts-expect-error' directive"*; with the symbol brand it passes — so
  the test discriminates between the two designs rather than passing either way.

## 9. Findings

### Critical

**C-1 — Migration 0037 could not apply to any database.** *(fixed)*
All 29 composite FKs added before their `(tenant_id, id)` target indexes exist → SQLSTATE 42830 on the
first one, whole migration aborts. Neither `IF NOT EXISTS` nor the `duplicate_object` handlers help.
Root cause of it going unnoticed: §22.2 #10's fresh `0000→0037` replay was never run.
`src/db/migrations/0037_unknown_siren.sql:195` (pre-fix) · §10.11.4, §22.2 #9/#10

**C-2 — `PolicyDecision` was forgeable, so §8.10 rule 3 did not hold.** *(fixed)*
`readonly __brand: 'WizmatchPolicyDecision'` is a plain string field; TypeScript is structural, so any
caller could write that literal and fabricate an `allow`. The whole chokepoint design rests on a sender
being unable to do this. Now a module-private `unique symbol`.
`policyTypes.ts:108` (pre-fix) · §8.10 rule 3, §22.2 #13

### High

**H-1 — §8.6's "restricted is not uniformly denied" was defeated.** *(fixed)*
The terminal return zeroed `allowedCampaignTypes`/`allowedOutreachModes` whenever the compatibility
decision was `deny`, making §8.6's and §8.7's own tables unreachable: `msp_vms_only` lost its `msp_vms`
research route, `direct_hiring_only` lost `research_only`, and every account-managed relationship
override lost `account_managed`. §8.9 defines `[]` as "none permitted", not "denied".
`outreachGate.ts:286-287` (pre-fix) · §8.6, §8.7, §8.9

**H-2 — L1c hardcoded `preparationAllowed: true`.** *(fixed)*
A `compliance` block at a narrower scope kept enriching and preparing a company that had formally asked
to be removed — the continued-PII-processing failure §8.9/H-1 was written to prevent, reintroduced one
level down. Every other level derived it correctly.
`outreachGate.ts:206` (pre-fix) · §8.9, §22.2 #20

**H-3 — Suppression read lowercased the input but not the stored column.** *(fixed)*
§8.10 is explicit: "both sides lowercased at read". A row written by any path that bypasses
`normalizeChannelValue` carries mixed case and would never match — the exact A-1-class gap the gate
exists to close, and invisible to the test suite because the mock ignores predicates.
`outreachGate.ts:79` (pre-fix) · §8.10, §20.1

**H-4 — Reason codes did not name the real cause.** *(fixed)*
L7 reported `email_hard_bounce` for **every** suppression hit including `contacts.do_not_contact` —
§8.5 is explicit that a bounce is a channel-quality fact and an unsubscribe is a stated preference, so
this writes a false fact into the audit trail PR 3 will depend on. Separately, every review reported
`policy_unknown_cold_start` regardless of cause, and terminal denies carried **no reason code at all**.
`outreachGate.ts:278, 288` (pre-fix) · §8.5, §9

**H-5 — L5 duplicate-suspect containment was not implemented.** *(fixed)*
`wizmatch_company_duplicates` was created by 0037 and never read, so A-14 and §8.8 were unenforced.
§22.2 #14 requires L0–L8. Now enforced on both sides of the ordered pair.
`outreachGate.ts:18-20` (pre-fix) · §8.2 L5, §8.8, §22.2 #14

### Medium

**M-1 — `campaignCompatibility.ts` kept a second hand-written `preparationAllowed` list.** *(fixed)*
Exactly the "second hand-written list" §8.9/H-1 forbids. Values happened to agree with the taxonomy,
but nothing tied them together and no test cross-checked them. Now derived via `isPreparationAllowed`.

**M-2 — `accountOwnerUserId` was always `null`.** *(fixed)*
§8.7 routes `existing_client` to `wizmatch_companies.account_owner_user_id`, so the `account_owner`
route was returned with no owner — unactionable. Now populated, with the documented null fallback.

**M-3 — `former_client` never contributed `reengagement`.** *(fixed)*
§8.7 names it; `RelationshipOverride` had no slot for a campaign-type contribution.

**M-4 — No test pinned the SQL state lists to the exported constant.** *(fixed)* §22.2 #8, §10.6.2.

**M-5 — The gate test mock discards `.where()`.** *(mitigated, not removed)*
The new contract suite captures predicates; the original suite still does not. Worth converging in PR 3.

**M-6 — `lower(email)` defeats the `(tenant_id, email)` index.** *(open, PR 3)*
The H-3 fix makes the suppression read a sequential scan. Correct beats fast here — but PR 3 should add
an expression index on `lower(email)` before any caller runs this per-recipient in a send loop. Not
added in PR 2: it would mean a new statement in a spec-frozen migration.

**M-7 — The resolver defaults missing dimensions via `??` rather than failing closed.** *(open)*
`relationshipType ?? 'new_prospect'` and `hiringPolicy ?? 'unknown'` rely entirely on the DB CHECKs. The
CHECKs are present and correct, so this is defence-in-depth, not a live hole — but §8.10 rule 5 names
"malformed persisted enum" as a fail-closed case and this would silently allow instead.

### Low

**L-1 — `evidence_kind` has no enumerated CHECK.** The D-7 CHECK asserts `evidence_kind IS NOT NULL` but
never `IN (…the six…)`. This matches the PRD's own SQL sketch, so it is a spec gap rather than a
deviation — but every other categorical column in this migration has an enum CHECK.

**L-2 — §10.10 says "22 entity references"; its own table unpacks to 29.** PRD wording.

**L-3 — §22.2 #1 says "seven new tables" but cites §10.1–§10.7 *and* §10.9.1, which is eight.** PRD wording.

**L-4 — No index supports a `company_b_id`-only duplicate lookup.** The new L5 query uses
`OR (company_a_id, company_b_id)`; at current row counts this is fine, but it is a scan.

## 11. Remaining blockers

**B-1 — §22.2 #16 is not implemented.** *"Every company insert path writes the cold-start root policy
row in the same transaction."* No such write exists in this branch. Without it, §21.2 condition 4
("zero companies missing an effective policy") is satisfiable only for the instant after the backfill,
and every company discovered afterwards immediately re-breaks it — which is precisely the failure D-1
and A-30 were written to prevent. **Not fixed here** because it means editing company-insert call sites
outside `src/modules/outreach`, which is caller-adjacent work and needs an owner call on whether it
lands in PR 2 or PR 3. It must land **before** G2/G4 either way. *This is the one criterion still open.*

**B-2 — §22.2 #10's ten verifications have not been run.** Nine of ten need a live Postgres. The two
that were checkable from the file are now automated (ordering, state parity). The fresh `0000→0037`
replay, the production `information_schema` drift diff, and the shared-table lock measurement remain.

**B-3 — The immutability trigger is untested.** Its body was read and reasoned through and is correct —
it protects every decision column and permits only supersession metadata — but no test fires it. Needs
a live database.

**B-4 — §20.1 categories with no test:** tenant isolation of the resolver (the mock cannot express it),
a genuine thrown DB error on the fail-closed path, `business_unit` applicability (only `location` is
covered), and per-cell values for ~59 of the 64 routing combinations.

## 14. Final recommendation

**Approve PR 2 with the four corrective commits, on the explicit condition that B-1 and B-2 are closed
before G1/G2.** The design is sound and the schema is the strongest tenancy work in this repo. The
defects were concentrated in two places — statement ordering the generator could not get right, and the
terminal decision assembly — and both are now covered by tests that fail on the defect rather than tests
that merely pass.

The process lesson is worth recording: **every one of C-1, H-3 and H-5 survived a fully green test
suite.** C-1 because the required replay was skipped; H-3 because the mock discards the predicate it was
supposedly asserting on; H-5 because nothing tested a table that nothing read. A green suite that cannot
fail is not evidence. §22.2 #10 exists for exactly this reason and should not be waived again.

Do not apply 0037. Do not promote enforcement. Do not begin PR 3 until B-1 has an owner decision.
